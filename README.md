# NODIA プロトタイプ要件書

## 1. 目的

学生向け情報整理・学習システム「NODIA」のプロトタイプを作る。NODIAでは、勉強・課題・予定・活動などの情報をノードとして整理し、必要に応じて接続して学習にも活用する。初期プロトタイプの実装対象は学校の5教科に絞る。ノードを視覚的に情報を扱う単位とし、ノードに機能を持たせたり、その中で使える機能を組み込んだりする。将来的には、利用者自身が記述した問題・図形の定義をNODIAが読み取り、操作できる学習UIへ変換できることを目指す。

本書は、既存実装を調べたうえで必要な範囲だけを拡張するための要件である。実装方式がまだ決まっていない点は、後半の「未決事項」に残す。

## 2. 対象ユーザーと教科

対象ユーザーは学生。初期プロトタイプの教科は次の5つとする。

- 国語
- 数学
- 英語
- 理科
- 社会

教科は学習内容や利用できる機能を整理する単位として扱う。5教科以外への拡張は、今回の必須要件に含めない。

### 2.1 学生の情報を扱う長期的な範囲

NODIA全体では、学生が学業を中心に、課題・授業予定・学習記録などを関連づけて管理できることを目指す。将来的には大学、起業、創作活動など、学業以外の情報も同じ基盤で扱える構想がある。初期プロトタイプでは範囲を広げず、5教科の学習ノードを中心に実装する。

## 3. 中心概念

### 3.1 ノード

ノードは情報を格納するだけの箱でも、開発者向けの処理ブロックでもない。学習者が情報を視覚的に整理し、読んだり操作したりするための単位である。ノードの中には、テキスト、問題、図形、計算機などを表示できる。ノードやその中身はUIであり、必要に応じて動作する機能そのものでもある。

例：

- 「数学の基礎」のような親ノードの内側に、計算機ウィジェットや図形問題ウィジェットを実体として配置できる。
- 計算機は「計算機」という名前の箱だけではなく、表示部とボタンを持ち、その場で計算できるUIとして親ノード内で動作する。
- 図形問題は問題文だけでなく、問題に必要な図形と操作を含む。たとえば数Aの円と接線の問題では、円・接線・点などを表示し、問題を解くために必要な点の移動や条件設定を行える。
- テキストノードは本文や解説を読みやすく表示する。

ノードの種類によって、表示内容や操作は異なりうる。すべてのノードを同じ見た目・同じ操作に揃えることを前提としない。

### 3.2 入れ子と接続の違い

ノードを別のノードの中に置く「包含」と、ノード同士を線で結ぶ「接続」は、別の意味として扱う。

- 包含は、親ノードが学習の場・まとまりになり、その内側で子ノードやウィジェットを表示・利用する関係。例：「数学の基礎」の中に計算機と図形問題を置く。
- 接続線は、ノード間の関連を視覚的に示すもの。線を作成・削除できる。線だけで親の中に子が入っていることを表現したことにしない。
- 入れ子は複数段にできることを念頭に置く。ただし、既存モデルで包含と線の意味をどう表現するか、初期版で何段まで操作可能にするかは既存コードを調べて決める。

### 3.3 大元のノードツリー

ユーザーが持つ情報の大元のノードツリーを、情報を保持・管理する基盤とする。ノードは必要に応じて他のノードや機能から参照できる。同じ情報をキャンバスごとに複製して別管理するのではなく、大元のノードを必要な場所で表示・利用する構造を目指す。

### 3.4 キャンバス

キャンバスは、ユーザーが情報を自由に並べ、整理し、表現する作業空間である。「テーブルの上にノードを置き、その上にルーズリーフを広げて作業する」イメージを基本とする。キャンバス上のノードやノードツリーの一部は、大元のデータを参照して表示する。

将来的なキャンバス要素にはノード、付箋、Markdown、画像、手書き・描画、ノードツリーの一部分などが含まれる。初期プロトタイプで必須なのは既存キャンバスとノード表示を活かすことであり、付箋・画像・描画などを一度に実装することではない。

役割の整理：

```text
大元のノードツリー = 情報を保持・管理する基盤
キャンバス           = 情報を自由に配置・表現する作業空間
ノード               = 情報への入口であり、必要に応じて機能を持つ
接続                 = ノード間の関係を表現する
```

### 3.5 構造編集と利用

ノードの配置・包含・接続を編集する操作と、ノード内の文章や機能を使う操作は、役割として区別する。編集画面と利用画面をどう構成するかは、既存UIと操作の分かりやすさを見て決める。

全ノードに独立したプレビュー画面を設けることや、ツリーと利用画面を必ず別画面にすることは要件ではない。ウィジェットは親ノードの中で直接使える形を基本イメージとする。

### 3.6 利用者が記述して画面にする

利用者が毎回AIに実装を頼まなくても、問題や図形の内容を自分で入力し、NODIAがそれを読み取って操作可能なUIに変換できることを目指す。

- 初期段階では、任意のプログラムを実行する仕組みではなく、問題文・図形要素・操作・条件などを決められた書式で記述する方法を検討する。
- 記述を解析し、入力ミスや未対応の記述を分かりやすく示し、対応するUIを生成する。
- 初期の記述例として、問題文、円、接線、点、ドラッグ可能な点などを扱える可能性を調べる。
- 記述形式（独自DSL、YAML/JSON、その他）は未決。学びやすさ、編集のしやすさ、既存アプリとの相性を確認して決める。
- AIは必須の実行時依存にしない。基本的な記述からの変換はアプリ内で再現可能にする。

## 4. 機能要件

### 4.1 5教科の基本機能

- 5教科を識別して表示できる。
- 各教科に属するノードや学習内容をツリー状に整理・閲覧できる。
- ノードを選択したとき、そのノードの内容または機能を表示・利用できる。
- 初期データや画面上で、教科・ノード・機能の対応関係を確認できる。

### 4.2 教科固有の機能

- 数学には、親ノードの中で使える計算機ウィジェットと、図形を含む問題を作成・利用するための図形問題ウィジェットを用意する。
- 計算機ウィジェットは計算機として見えるUIと動作を一体で持つ。
- 図形問題ウィジェットは、問題に必要な図形を表示し、問題を解くための操作・設定ができる。テストなどの図形問題を作り、解けることを目指す。
- 最初の具体例は「円と接線」など、数A相当の問題を想定する。どの作図要素・幾何制約・操作を初期対応するかは既存実装を調べ、実現範囲を明示する。
- 国語、英語、理科、社会については、5教科として選択・整理できる基礎を作る。会話で具体化されていない専用機能を勝手に追加せず、既存機能とプロトタイプ規模に合わせる。
- 課題・予定・学習記録などに機能を持たせる構想はあるが、初期版で5教科以外の機能まで一度に実装しない。
- 初期段階ではノード種別と対応機能を固定してよい。利用者が自由に任意の機能を作成できる汎用プラグイン機構は必須ではない。

### 4.3 教科をまたいで再利用できる機能

- ノードをピン留めできるなど、複数教科で共通利用できる機能を想定する。
- ピン留めの保存範囲や表示場所は、既存のユーザー・データ構造を確認して決める。
- 共通機能と教科固有機能を、必要に応じて区別して扱える設計にする。

### 4.4 機能の選択・呼び出し

- 利用者が必要な機能を選んで使える、スマートフォンのコントロールセンターのような考え方を参考にする。
- 例として、計算機などの機能へすぐアクセスできる方法を検討する。
- ノードに固定機能を割り当てることと、親ノード内に機能ウィジェットを含めることを基本にする。共通機能パネルを設けるかは既存UIを調査したうえで決める。
- すべての機能を常時表示する必要はない。プロトタイプでは、利用者が機能を見つけて起動できる最小限の導線を作る。

## 5. 既存プロジェクトを調べてから実装すること

実装前にワークスペース全体を調査し、構成と既存機能を報告する。会話時点のプロジェクト情報では、Djangoアプリに `Subject`、`Node`、`NodeConnection` モデルとテンプレートが存在する。実際のファイル・現在の状態を必ず確認し、この情報を前提として決めつけない。

調査では少なくとも次を確認する。

- Djangoアプリ、URL、ビュー、テンプレート、静的ファイルの構成
- `Subject`、`Node`、`NodeConnection` のフィールド、制約、関連
- ツリー表示・ノード表示・ノード操作の現状
- 管理画面、初期データ、認証やユーザー別データの扱い
- 既存のテストや実行方法、プロジェクト固有の指示書
- 今回の要件を既存構造で実現できる範囲と、必要な最小変更

調査結果を簡潔に説明してから実装に進む。既存設計で対応できる部分は活用し、不要な全面書き換え、モデルの重複、過剰な抽象化を避ける。モデル変更が必要な場合は、理由を明確にし、Djangoのマイグレーションを含めて整合させる。

## 6. 実装の進め方

1. ワークスペース全体を調査し、既存アーキテクチャ、マイグレーション、実際に使われるデータベースを報告する。
2. 既存機能と要件の対応を整理し、追加・変更が必要な最小範囲を定める。
3. 5教科を扱う基本導線を実装する。
4. 親ノード内に子ノード／ウィジェットを配置して使う最小の縦断機能を実装する。
5. 計算機の見た目と動作を持つウィジェットを数学の親ノード内で使えるようにする。
6. 図形問題について、記述から表示・操作へ変換する小さな一連の例を作る。初期対応の範囲と制約を明示する。
7. ピン留めなど、既存構造と整合する共通機能を扱う。
8. 実装内容、変更点、未対応事項、確認方法を報告する。

## 7. プロトタイプの完了条件

- 5教科を画面上で識別して扱える。
- 教科内のノードをツリー状に確認できる。
- ノードを選択して内容または機能を利用できる。
- 「数学の基礎」のような親ノードの中に、子ノードやウィジェットを含められる。
- 計算機が単なる名前の箱ではなく、計算機のUIと動作を持ち、親ノード内で使える。
- 図形を必要とする問題を、対応する範囲で記述し、図形と操作を画面に表示できる。対応範囲と制約が明示されている。
- ピン留めなど共通機能を少なくとも一つ、既存構造に沿って試せる（既存の認証・データ構造により実装範囲が変わる場合は、その理由を報告する）。
- ツリーの構造を扱う操作とノード機能を使う操作の役割が利用者に分かる。
- 既存アーキテクチャと変更箇所、実行・確認方法が説明されている。
